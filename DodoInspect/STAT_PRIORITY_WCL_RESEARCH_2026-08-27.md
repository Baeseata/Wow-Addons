## 3. 实测:三个问题全部有答案了(而且比预期好得多)

⚠ 下面每个数都是 API 自己回的,不是记忆。

### A. 额度 = **3600 点 / 小时**

`Query.rateLimitData { limitPerHour, pointsSpentThisHour, pointsResetIn }`。
标定过:**一次 `rateLimitData` 读数本身就要 1.000 点**(连读三次:14.020 → 15.020 → 16.020),
所以量别的查询要把这 1 点扣掉。

### B/C. 🔑 `characterRankings` 有个 `includeCombatantInfo: Boolean` 参数 —— 装备直接跟着排行榜回来

**这一条把整个项目的成本量级改了。** 不需要「排行榜一次 + 每个人的战报再一次」——
**一次查询就把 100 个人连装备一起给你**:

```graphql
worldData { encounter(id: $e) {
  characterRankings(metric: dps, page: 1, includeCombatantInfo: true,
                    className: "Shaman", specName: "Enhancement") } }
```

- ⚠ **订正:一次调用实测 = 2.02 点**(原写 `≈ 1.01`,**正好差一半**),返回 **最多 100 条**。
  错因就在上一段:那里刚说完「一次 `rateLimitData` 读数本身要 1 点,量别的要把它扣掉」——
  而这个数**已经扣过一次了**,我又扣了一遍。
  🔑 **标定量和被标定量在同一次读数里时,把「这一点到底减了没有」写出来** ——
  两种算法各自自洽,而差的正好是 2 倍,事后从数字上分不出来。
  全量跑完拿 674 次新调用的实际扣费反推,才把它钉死在 2.02(`POINTS_PER_CALL`)。
- 开了 `includeCombatantInfo` 之后每条多出 `gear` / `talents` / `externalBuffs` / `faction`
- `gear` = 18 个部位,每件带 **`id` · `itemLevel` · `bonusIDs` · `gems` · `permanentEnchant`**
- ⛔ **没有** `stats` 字段 —— 属性要**从装备反推**,不是现成的

| 大米 | **55 Mythic+ Season 2**(未冻结) | 8 个本 | 320 | ~646 |
| | | | **680 次** | **≈ 1374 点** |

(另 6 个来自之前 `--only 581` 的试跑,缓存里共 680 个文件)。
现在这三个数不用再手算,`--plan` 自己会打:
`plan: 17 encounters x 40 specs = 680 calls, ~1374 points (38% of the 3600/hour limit). Nothing spent.`

### 样本量:**按专精差很多,这是真正的限制**

同一个 boss 上实测:惩戒骑 100+ · 神牧 100+ · 增强萨 58 · **冰法只有 13**。
(`count = 100` 是**页上限**,意思是「至少 100」;只有小数字才是精确值。)
⇒ **冷门专精的「趋势」可能建立在十几个人身上**,报结论必须带样本量,
别让一个 13 人的分布和一个 100 人的分布长得一样权威。

### ⚠ 订正:剩下的真活**不是** item id → 副属性

〔原文〕`gear` 给的是物品 id + bonusIDs,**不是属性**。拿一个真样本比对:18 件里 **9 件**
已经在我们自己的 `Data/Loot.lua` 里,另外 9 件是本季团本套装 / 衬衣 / 战袍 / 旧物品。
⇒ 走 `gen_loot.py` 已经在用的 **DB2 `ItemSparse`** 现查。
~~**这是这个项目唯一真正要写的一段代码**~~ ← **这句错了。**

**动手之后**:`ItemSparse` 那半基本是**复用 `gen_loot.py` 的 `read_stats`** —— 同一张表、
同一组 `StatModifier_bonusStat_*` / `StatPercentEditor_*` 列、同一个属性 id 空间,没有新东西。

🔴 **真正的活是:bonusID 会改「这件装备有哪两条副属性」,不只是改装等。**
`ItemSparse` 里有一批物品把副属性写成**哨兵** `24` / `25`(一对 3500+3500 的通配槽,
基础行里**没有属性身份**;抽样 475 个 id 里有 **41 个**);身份是**穿在身上那一件**
通过 `ItemBonus` 的 `Type=25` 行带来的,六个 bonusID 覆盖全部六种「四选二」组合
(8790 暴+急 · 8791 暴+精 · 8792 急+全 · 8793 急+精 · 8794 精+全 · 8795 暴+全)。

- **失败方向是静默的**:只读基础行 ⇒ 这些装备被当成「没有副属性」丢掉,而报表照样长得完整。
  全量负对照实测:**带 bonusID 解出 520,946 件,不带只有 465,528 件 —— 55,418 件被无声吞掉**。
- 🔑 **「物品 id → 属性」根本不是一个函数**:全量实测 **89 个** id 在不同角色身上解出**不同的属性对**
  ⇒ 缓存的键必须是「id + bonusIDs」,不能是 id。
- 守它的是断言 4 + `--verify` 的两条负对照(「通配解析是载重的」/「一个 id 解出多种」),
  两条都不是形式主义:把 `wild_map` 换成 `{}` 再跑一遍,上面那两个数就是它们的读数。

⇒ 顺带把宝石 / 附魔也接上了(`ItemSparse.Gem_properties` → `GemProperties.Enchant_ID` →
`SpellItemEnchantment.Effect/EffectArg`,属性 id 空间跟 `gen_loot.py` 一致)。
**数值大小解不了**(要 `GtSpellScaling` GameTable,wago.tools 不提供),但这里只数
「他们主动选了哪个」,不需要数值 —— 而这一列正是 §5 那条价值边界的解药,见下。

## 5. 这条路真正的价值边界(先想清楚再花钱)

- ✅ **它能回答**:「顶级玩家实际穿的装备,副属性分布偏向谁」——
  这是**观察**,置信度高,而且跟攻略作者的意见相互独立。
- ⛔ **它回答不了「应该堆什么」**。高手的属性分布里混着**掉落运气**、
  **装等优先于副属性**(本季两个源都明说「item level 压倒一切」)、
  以及**大家都在照同一批攻略配装**这个回音室效应。
  ⇒ **观察到的分布不是权重,它是「攻略 + 掉落 + 装等」的合成结果。**
- 🔑 所以正确的用法是**当反证不当正证**:某个专精我们写着「精通第一」,
  而 top 100 的精通含量垫底 —— 那值得回头查;反过来「他们精通高」**不证明**精通更好。

### 🔑 补(2026-08-27 全量跑完):上面那条边界比预想的**更紧**,而且有一半有解

**紧在哪**:第一版判据只比「他们的第一名 vs 我们的第一名」,80 行里报了 **25 条**分歧。
逐条量了一下领先幅度 —— **20 条领先不到 5 个百分点、11 条不到 3 个、有一条只有 0.2 个**。
⇒ 那 25 条里绝大多数量的**不是玩家偏好,是掉落池的偏斜**:穿什么受供给约束,
**掉落表决定了「有什么可穿」**,而一个 boss 掉的东西副属性组合本来就不均匀。

**有解的那一半 = 宝石和附魔**。它们**不受供给约束** —— 想镶哪个镶哪个,是纯粹的主动选择。
⇒ 判据改成**两道闸同时过**:① 领先幅度 ≥ `MIN_MARGIN`(3 个百分点)**且**
② 他们**自己挑的**那一列也跟我们不一致。

**加闸后那 25 条干净地裂成三堆**(7 + 11 + 7 = 25,天然的 A/B):

| verdict | 条数 | 含义 |
|---|---|---|
| **FLAG** | **7** | 穿的和挑的**都**跟我们不一致 —— 值得回头查的就这 7 条 |
| `thin` | 11 | 领先幅度太小,读不出信号 |
| `loot?` | 7 | 穿的跟我们不一致,**但他们的宝石附魔跟我们一致** ⇒ 这是掉落供给,不是偏好 |

🔑 **`loot?` 单独成一档,不是「弱一点的 FLAG」** —— 它是**关于世界的另一个事实**
(「这个专精想要的东西掉得少」),跟「我们可能写错了」是两件事,合并就把两个都读没了。

🔑 **可迁移的那条**:**拿一个观测分布当证据之前,先量它的领先幅度,再找一条
不受同一个约束的信道去印证它。** 只比排名 ⇒ 25 条待查;加上这两道闸 ⇒ 7 条,
而且**每一条都能说出它为什么值得查**。
